# 仲恺校园信息服务智能体开发顺序建议

> 文档用途：说明在已有项目说明文档后，下一步应该如何开始开发。  
> 核心结论：不要一开始就大规模采集全部校园资料，也不要只搭一个空骨架。最合理的方式是 **先搭最小项目骨架，再用少量真实校园资料跑通 AI / Agent 闭环**。

---

## 1. 总体建议

当前已经有项目说明文档，下一步不建议马上完整采集仲恺农业工程学院官网的全部资料。

原因是：

- 官网资料范围较大，主站和二级站点很多；
- 资料类型复杂，包括 HTML、PDF、DOC、DOCX、ZIP、通知公告、服务入口等；
- 如果先大规模采集，容易陷入数据清洗和整理，迟迟看不到系统效果；
- 如果只搭项目骨架，没有真实数据，又无法验证 RAG、智能文档和 Agent 是否能工作。

因此推荐采用：

```text
项目骨架
  ↓
少量真实校园资料
  ↓
RAG / 智能文档跑通
  ↓
Agent 路由跑通
  ↓
前端展示跑通
  ↓
再扩大资料采集范围
```

也就是说，第一阶段应该是：

> **轻量项目骨架 + 小批量真实资料 + AI 闭环验证。**

---

## 2. 不建议的两种做法

### 2.1 不建议先完整采集全部资料

如果一开始就采集完整官网，可能会遇到：

- 页面数量多；
- 栏目层级复杂；
- 附件格式不统一；
- 清洗规则难写；
- 有些附件可能带验证码或访问限制；
- 很难判断哪些信息应该优先进入知识库；
- 开发进度容易被数据采集拖慢。

完整资料采集应该放在系统闭环跑通之后。

---

### 2.2 不建议只搭空骨架

如果只搭目录、接口和页面，但没有真实校园资料，会导致：

- RAG 无法测试；
- 智能文档无法测试；
- Agent 路由无法验证；
- 来源引用无法展示；
- 项目演示效果不明显；
- 很难判断设计是否合理。

所以骨架搭建后，应尽快接入少量真实资料。

---

## 3. 推荐开发顺序

## 第 1 步：先搭一个最小项目骨架

先创建项目目录和基础模块，不需要一开始实现所有功能。

推荐项目结构：

```text
zhku-campus-agent/
├── backend/
│   ├── app.py
│   ├── agents/
│   ├── rag/
│   ├── tools/
│   └── database/
├── crawler/
├── data/
│   ├── raw/
│   ├── cleaned/
│   ├── metadata/
│   └── vector_store/
├── frontend/
├── docs/
└── README.md
```

这个阶段重点是确定项目基本技术路线：

- 后端使用 FastAPI 还是 Streamlit；
- 向量库使用 Chroma、FAISS 还是 Qdrant；
- 结构化数据先使用 SQLite 还是 JSON；
- 大模型 API 如何调用；
- RAG 检索接口如何设计；
- Agent 路由接口如何设计；
- 前端如何展示答案、来源、附件和工具调用结果。

本阶段目标：

> 项目能启动，有基本接口，有清晰目录，有后续扩展位置。

---

## 第 2 步：准备少量高质量真实资料

不要一开始爬完整个官网。建议先选 10～20 条最有代表性的资料，用于验证系统闭环。

优先选择以下资料：

| 类型 | 建议资料 |
|---|---|
| 学校基础信息 | 学校概况、校区地址、机构设置 |
| 专业信息 | 本科专业目录、1～3 个培养方案 PDF |
| 教务资料 | 学生证补办、缓考申请、成绩复查、免修申请 |
| 研究生资料 | 研究生招生章程、研究生免修 / 休学 / 请假申请表 |
| 公共服务 | 后勤联系方式、网络服务、校医院就医指引 |

这批资料不需要很多，但要覆盖不同类型：

- HTML 页面；
- PDF 文件；
- Word 文件；
- 下载资料；
- 结构化信息；
- 联系方式；
- 服务入口。

本阶段目标：

> 用少量真实资料测试网页清洗、文档解析、向量检索、智能文档和来源引用。

---

## 第 3 步：跑通一个完整 AI 闭环

项目重点是 AI / Agent，因此第一版必须尽快跑通以下闭环：

```text
用户提问
  ↓
Agent 判断问题类型
  ↓
选择 RAG / 智能文档 / 结构化工具
  ↓
检索官网资料或文档片段
  ↓
大模型生成回答
  ↓
返回答案 + 来源 + 附件入口
```

这一阶段不追求功能多，而追求流程完整。

---

## 4. 第一批建议支持的演示问题

建议先支持以下 5 个问题：

```text
1. 仲恺农业工程学院有几个校区？
2. 学校有哪些教学机构？
3. 补办学生证申请表在哪里？
4. 数据科学与大数据技术专业培养方案在哪里？
5. 2026 年硕士研究生招生章程主要讲了什么？
```

对应展示能力如下：

| 问题 | 展示能力 |
|---|---|
| 仲恺农业工程学院有几个校区？ | 官网 RAG |
| 学校有哪些教学机构？ | 结构化查询 |
| 补办学生证申请表在哪里？ | 资料下载查询 |
| 数据科学与大数据技术专业培养方案在哪里？ | 智能文档 + 附件检索 |
| 2026 年硕士研究生招生章程主要讲了什么？ | 智能文档摘要 / 文档问答 |

只要这 5 个问题能跑通，项目就已经具备核心雏形。

---

## 5. 第一阶段应该实现的核心能力

### 5.1 基础能力

第一阶段至少实现：

1. 项目可以启动；
2. 后端可以接收用户问题；
3. 系统可以调用大模型；
4. 系统可以读取少量校园资料；
5. 系统可以进行基础 RAG 检索；
6. 系统可以返回答案；
7. 系统可以展示来源。

---

### 5.2 AI / Agent 能力

第一阶段应重点体现：

1. Agent 能识别问题类型；
2. Agent 能选择不同处理路径；
3. Agent 能区分普通网页问答、智能文档问答和结构化查询；
4. Agent 能整合检索结果；
5. Agent 能在没有可靠资料时兜底；
6. Agent 能返回来源，而不是直接编造答案。

---

### 5.3 智能文档能力

第一阶段至少选择一个智能文档能力实现：

| 能力 | 说明 |
|---|---|
| 文档问答 | 围绕培养方案、招生章程、申请表进行提问 |
| 文档摘要 | 自动总结长文档的核心内容 |
| 关键字段抽取 | 提取材料、时间、地点、对象、联系电话 |
| 多文档对比 | 对比不同资料中的差异 |

建议优先做：

> **文档问答 + 文档摘要**

因为这两个功能最容易展示 AI 能力，也最符合项目“智能文档”的定位。

---

## 6. Agent 路由初版设计

Agent 路由可以先写成规则版，不必一开始就使用复杂的大模型路由。

示例代码：

```python
def route_question(question: str):
    if any(k in question for k in ["培养方案", "招生章程", "这个文档", "总结"]):
        return "document_rag"
    elif any(k in question for k in ["申请表", "下载", "表格"]):
        return "download_tool"
    elif any(k in question for k in ["电话", "联系", "地址"]):
        return "contact_tool"
    elif any(k in question for k in ["专业", "学院", "机构"]):
        return "structured_search"
    else:
        return "general_rag"
```

后续可以升级为大模型意图识别：

```text
用户问题
  ↓
LLM 判断意图
  ↓
输出 JSON 路由结果
  ↓
调用对应工具或 RAG
```

例如：

```json
{
  "intent": "document_qa",
  "tool": "document_rag",
  "keywords": ["硕士研究生招生章程"],
  "need_sources": true
}
```

## 7. 推荐 7 天开发节奏

### 第 1 天：项目骨架

任务：

- 创建项目目录；
- 初始化 Git；
- 编写 README；
- 配置 Python 环境；
- 搭建 FastAPI 或 Streamlit 最小服务；
- 准备 `.env.example`。

产出：

- 项目可以启动；
- 有基础目录；
- 有开发说明。

---

### 第 2 天：准备少量官网资料

任务：

- 收集 10～20 条代表性资料；
- 保存 URL、标题、来源部门、类型；
- 建立 metadata 表；
- 保存 HTML / PDF / Word 文件或入口信息。

产出：

- `data/raw/` 原始资料；
- `data/metadata/metadata.csv`；
- 初始资料清单。

---

### 第 3 天：实现网页和文档解析

任务：

- 实现网页正文提取；
- 实现 PDF 文本解析；
- 实现 Word 文本解析；
- 将资料转为 Markdown 或 TXT；
- 保存清洗后文本。

产出：

- `data/cleaned/`；
- 文档解析脚本；
- 清洗后的文本资料。

---

### 第 4 天：构建向量库和基础 RAG

任务：

- 文本切分；
- 生成 Embedding；
- 写入 Chroma / FAISS；
- 实现 Top-K 检索；
- 实现基础 Prompt；
- 返回答案和来源。

产出：

- 向量库；
- RAG 检索接口；
- 可以回答基础官网问题。

---

### 第 5 天：实现 Agent 路由和工具调用

任务：

- 实现问题类型判断；
- 实现结构化查询工具；
- 实现资料下载查询工具；
- 实现联系方式 / 服务入口查询工具；
- 实现智能文档问答或摘要工具。

产出：

- Agent Controller；
- tools 模块；
- 支持多路径处理问题。

---

### 第 6 天：前端展示

任务：

- 做一个简单 Web 页面；
- 支持用户输入问题；
- 展示 AI 回答；
- 展示来源 URL；
- 展示附件入口；
- 展示工具调用类型。

产出：

- 可演示前端；
- 基础聊天界面；
- 来源展示组件。

---

### 第 7 天：扩充资料和准备演示

任务：

- 扩充一部分资料；
- 准备演示问题；
- 测试 RAG 检索准确率；
- 测试智能文档问答；
- 测试无依据兜底；
- 整理截图和演示说明。

产出：

- 演示问题集；
- 测试结果；
- 项目展示材料初稿。

---

## 8. 阶段性开发路线

### 第一阶段：轻骨架 + 小数据

目标：

- 搭建项目基础结构；
- 接入少量真实校园资料；
- 验证 AI 闭环。

重点：

- 不追求资料多；
- 不追求页面多；
- 优先跑通 RAG、智能文档和 Agent 路由。

---

### 第二阶段：AI 闭环优先

目标：

- 完成 Agent 主控；
- 实现基础意图识别；
- 接入 RAG；
- 接入智能文档；
- 接入结构化工具；
- 实现来源引用和兜底。

重点：

- 用户提问后，系统不是固定搜索；
- Agent 能主动判断使用哪种能力；
- 回答必须有来源；
- 没有依据时不胡编。

---

### 第三阶段：扩大资料规模

目标：

- 扩大官网采集范围；
- 增加更多二级站点；
- 完善资料下载中心；
- 增加更多智能文档；
- 增强新闻公告和就业信息检索。

重点：

- 在系统闭环稳定后再扩充数据；
- 采集策略要配置化；
- 每条资料都要有来源和更新时间。

---

## 9. 最佳路线总结

当前最适合的路线是：

```text
第 1 步：搭最小项目骨架
第 2 步：准备 10～20 条真实官网资料
第 3 步：实现网页 / PDF / Word 解析
第 4 步：构建向量库 + 基础 RAG
第 5 步：实现 Agent 路由 + 工具调用
第 6 步：做前端问答页面 + 来源展示
第 7 步：扩充资料 + 准备演示问题
```

最终结论：

> **先搭大致骨架，但必须马上接入少量真实校园资料验证 AI 闭环。不要等资料全采完再开发，也不要搭一个没有真实数据的空系统。**

项目第一阶段最重要的不是资料数量，而是证明：

```text
真实资料
  ↓
RAG / 智能文档
  ↓
Agent 判断与调用
  ↓
可信回答
  ↓
来源展示
```

这个闭环能够真正跑通。
