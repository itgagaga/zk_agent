## 1. 文档目的

本文档是在原“校园生活服务智能体项目说明”基础上，结合仲恺农业工程学院官网当前可公开获取的信息重新整理形成的项目立项与开发说明。

本次修改的核心原则是：

- 不再把“校园网、图书馆预约、宿舍报修”等作为固定功能；
- 不再按照泛化高校场景凭空设计功能；
- 以仲恺农业工程学院官网及其公开二级站点中真实存在、资料较完整、可采集、可引用的信息为依据；
- 将项目定位从单纯“校园生活助手”升级为“面向学生和教师的学校信息服务智能体”；
- 将功能范围聚焦在学校概况、机构学院、专业培养、招生就业、教务服务、研究生教育、公共服务、资料下载和新闻公告等可落地模块；
- 进一步突出 AI / Agent 主动能力，避免项目被理解为普通官网聚合、资料搜索或静态知识库；
- 新增“智能文档”能力，将官网网页、PDF、Word、招生章程、培养方案、申请表、政策制度等资料转化为可问答、可摘要、可对比、可引用的智能文档。

本文档可用于项目前期立项、需求分析、分工开发、系统设计、MVP 开发和后续项目报告撰写。

## 2. 选题背景

本项目需要围绕真实学校场景，开发一个可运行、可演示、可扩展的智能体系统。系统应体现以下能力：

- 大语言模型接入；
- RAG 检索增强生成；
- 工具调用 / 本地 API 调用；
- 结构化数据查询；
- 前后端交互；
- 数据采集与知识库构建；
- 来源引用与可信回答；
- 项目部署和演示材料。

结合仲恺农业工程学院官网信息，学校公开网站具有以下特点：

1. **信息丰富**  
   官网和二级站点公开了学校概况、发展历史、校区地址、机构设置、学院信息、本科专业、培养方案、本科招生、研究生招生、就业服务、教务资料下载、后勤服务、网络服务、校医院、采购招标、人才招聘等内容。

2. **信息分布广**  
   信息分布在学校主站、教务部、研究生处、就业指导中心、总务后勤部、现代教育技术中心、校医院、招生系统等多个站点中。

3. **用户查找成本高**  
   学生和教师往往不知道某类信息属于哪个部门、哪个二级站点、哪个栏目，容易出现“找不到入口”“不知道关键词”“找到了但不知道是否适用”的问题。

4. **适合构建知识库与智能体**  
   这些公开网页、通知、附件、表格、联系方式和服务指南非常适合构建 RAG 知识库，也适合抽取为结构化数据供工具调用。

因此，本项目选择围绕仲恺农业工程学院公开网站建设一个面向学生和教师的校园信息服务智能体。

## 3. 项目定位

### 3.1 一句话定位

> **ZHKU Campus Agent 是一个基于仲恺农业工程学院公开网站信息构建的校园信息服务智能体，面向学生、教师和访客提供学校信息问答、办事资料检索、服务入口导航和可信来源展示。**

### 3.2 项目边界

本项目不是简单的聊天机器人，也不是完整替代学校官网的门户系统。

本项目的合理定位是：

| 项目内容 | 是否包含 | 说明 |
|---|---:|---|
| 学校公开信息问答 | 是 | 基于官网和二级站点公开内容回答 |
| 学院、机构、专业查询 | 是 | 基于官网机构设置和教务部专业目录 |
| 招生、研究生、就业信息导航 | 是 | 基于招生就业页、研究生处、就业指导中心 |
| 教务资料、培养方案、申请表查询 | 是 | 基于教务部公开下载栏目和培养方案页面 |
| 公共服务入口导航 | 是 | 包括后勤、网络、校医院、采购招标、邮箱、VPN 等公开入口 |
| 新闻公告聚合 | 是 | 采集学校要闻、通知公告、校园快讯等公开动态 |
| 个人课表、成绩、财务、人事数据 | 否 | 需要统一身份认证和学校授权，不作为 MVP 范围 |
| 代办申请、自动提交表单 | 否 | 涉及权限和流程审批，暂不实现 |
| 登录型系统深度接入 | 否 | 只做入口导航，不抓取登录后数据 |

### 3.3 与原文档相比的主要变化

原文档以“校园生活服务”为主，功能示例较泛化。本版根据当前网站信息做出以下调整：

- 项目名称从 **CampusLife Agent** 调整为 **ZHKU Campus Agent**；
- 核心目标从“校园生活事务办理指引”扩展为“学校信息服务与资料检索”；
- 功能依据从“常见校园生活问题”调整为“官网真实公开栏目和资料”；
- MVP 不再强行覆盖图书馆预约、校园卡挂失等未确认资料，而优先覆盖官网资料完整的模块；
- 新增“学院专业库”“培养方案库”“资料下载库”“服务入口导航库”“招生就业知识库”等更贴合仲恺官网的信息模块；
- 工具调用从天气等通用工具调整为更贴合项目的数据查询工具，例如专业查询、部门联系方式查询、资料下载查询、服务入口查询、通知公告检索。

### 3.4 AI / Agent 主线说明

本项目的重点不应只是“把仲恺官网信息整理到系统里”，而应体现 **AI / Agent 如何主动理解问题、选择工具、检索证据、处理文档并生成可信答案**。

官网公开信息只是系统的知识来源，AI / Agent 才是项目的核心能力。项目展示时应突出以下主线：

```text
用户自然语言问题
  ↓
Agent 理解意图
  ↓
判断问题类型
  ├── 学校信息问答
  ├── 专业 / 学院 / 机构查询
  ├── 招生 / 研究生 / 就业查询
  ├── 教务资料 / 表格下载查询
  ├── 智能文档问答
  ├── 多文档对比
  ├── 服务入口 / 联系方式查询
  └── 无可靠依据兜底
  ↓
自动选择 RAG、结构化工具或文档工具
  ↓
整合网页证据、文档片段、附件信息和结构化数据
  ↓
生成带来源、带解释、可追溯的回答
```

因此，本项目应被描述为：

> **一个以 Agent 为核心调度器、以 RAG 和智能文档为知识底座、以学校官网公开资料为数据来源的校园信息服务智能体系统。**

### 3.5 AI / Agent 占比是否合理

从 v0.2 文档来看，已经包含 RAG、工具调用、智能体工作流、结构化查询和无依据兜底等内容，但整体篇幅仍然偏向“网站信息有哪些、系统能查什么”。这对项目立项有帮助，但如果项目评审重点是 AI 或 Agent，当前表达还不够突出。

建议在最终项目中按以下比例组织重点：

| 内容方向 | 建议占比 | 说明 |
|---|---:|---|
| AI / Agent 能力 | 35% - 45% | 意图识别、任务路由、工具选择、RAG 编排、文档理解、答案生成、兜底策略 |
| RAG 与智能文档 | 25% - 30% | 官网网页、PDF、Word、表格、章程、培养方案、申请表的解析、切分、检索、引用 |
| 网站信息与业务模块 | 15% - 20% | 学校概况、机构学院、专业培养、招生就业、教务服务、公共服务等 |
| 前后端与工程实现 | 10% - 15% | FastAPI、前端页面、数据库、向量库、部署、管理后台 |
| 测试评估与展示 | 5% - 10% | 演示问题、检索准确率、引用完整率、无依据兜底测试 |

也就是说，文档中可以保留网站资料分析，但项目汇报和系统实现要把重点放在：

- Agent 如何判断用户想问什么；
- Agent 如何决定用网页 RAG、文档 RAG、结构化工具还是混合查询；
- Agent 如何处理 PDF / Word 等智能文档；
- Agent 如何保证回答有来源、不胡编；
- Agent 如何把复杂问题拆成多个步骤；
- Agent 如何返回可操作的网页、附件、表格和服务入口。

### 3.6 “网站信息”与“智能文档”的关系

本项目的信息来源可以分为两层：

#### 第一层：网站公开信息

包括官网 HTML 页面、通知公告、栏目列表、服务入口、联系方式、学院专业列表等。

这部分适合做：

- 学校信息问答；
- 机构学院导航；
- 服务入口查询；
- 联系方式查询；
- 新闻公告检索；
- 结构化数据抽取。

#### 第二层：基于网站资料构建的智能文档

官网中的 PDF、DOC、DOCX、ZIP 附件，以及网页中的章程、制度、培养方案、办事流程等，可以转化为智能文档。

这部分适合做：

- 文档问答；
- 文档摘要；
- 文档目录解析；
- 关键字段抽取；
- 跨文档对比；
- 条款解释；
- 表格和申请材料提取；
- 生成办理清单；
- 根据用户身份生成个性化说明。

因此，系统不只是“从网站找信息”，还应支持：

> **把官网资料变成可交互的智能文档，让学生和教师可以像问 AI 一样阅读培养方案、招生章程、教务表格、医保政策、研究生管理文件和各类办事指南。**

## 5. 目标用户与核心问题

### 5.1 目标用户

本项目主要面向：

- 在校本科生；
- 在校研究生；
- 教职工；
- 新生；
- 考生及家长；
- 访客；
- 系统管理员和内容维护人员。

其中 MVP 第一版优先服务 **学生和教师**，兼顾考生和访客的信息查询需求。

---

### 5.2 用户痛点

当前用户在了解学校信息时，可能遇到以下问题：

1. **入口分散**  
   学校信息分布在主站和多个二级站点，例如教务部、研究生处、就业指导中心、总务后勤部、现代教育技术中心、校医院等。

2. **不知道该找哪个部门**  
   例如学生想找成绩复查表、缓考申请表、研究生请假表、医保报销材料，可能不知道应进入哪个栏目。

3. **资料类型复杂**  
   信息既有网页，也有 PDF、DOC、DOCX、ZIP、通知、表格、流程图等，普通搜索不易统一管理。

4. **角色需求不同**  
   学生关注专业、培养方案、教务表格、医保和就业；教师关注 OA、人事、科研、网络服务、教学资源；考生关注招生章程、专业目录和录取情况。

5. **普通大模型容易编造**  
   如果不接入真实网站资料，大模型可能给出不准确的电话、地点、流程和时间。

6. **官网信息更新频繁**  
   招生、就业、公告、后勤、网络、校医院等内容具有时效性，需要定期采集与更新。

---

### 5.3 项目要解决的问题

本项目希望解决：

> 如何将仲恺农业工程学院公开网站信息整合为可检索、可引用、可交互的智能服务入口，使学生和教师能够通过自然语言快速了解学校、查找部门、查询专业、获取资料、定位服务入口，并看到可靠来源。

---

## 6. 初步需求分析

### 6.1 功能性需求

系统应至少支持以下功能。

#### 6.1.1 自然语言问答

用户可以直接输入中文问题，例如：

- 仲恺农业工程学院有几个校区？
- 学校有哪些学院？
- 人工智能学院网址是多少？
- 本科专业目录在哪里看？
- 计算机科学与技术专业有没有培养方案？
- 研究生免修课程申请表在哪里下载？
- 学生证补办表在哪？
- 校医院报销需要什么材料？
- 网络报障电话是多少？
- 后勤维修科电话是多少？
- 教师常用的 OA、邮箱、VPN 入口在哪里？

系统应基于官网资料生成简洁、准确、可追溯的回答。

---

#### 6.1.2 RAG 检索增强生成

系统应从已采集的官网网页、通知、服务指南、下载页面、培养方案和规章制度中检索相关片段，再交给大模型生成回答。

回答中必须尽量展示：

- 来源标题；
- 来源部门；
- 来源 URL；
- 发布时间或更新时间；
- 命中的文本片段；
- 如果是附件，展示附件名和来源页面。

---

#### 6.1.3 学校信息知识库

系统应建立学校基础知识库，覆盖：

- 学校简介；
- 历史沿革；
- 校区地址；
- 联系电话；
- 办学规模；
- 学科专业；
- 学院和部门；
- 教辅科研平台；
- 公共服务入口。

---

#### 6.1.4 学院与专业查询

系统应支持：

- 根据学院查专业；
- 根据专业查学院；
- 根据专业名称查培养方案；
- 根据专业代码查专业；
- 查询本科专业目录；
- 查询某个学院官网入口；
- 面向考生展示专业相关资料。

---

#### 6.1.5 资料下载检索

系统应建立“资料下载库”，支持查询：

- 教务申请表；
- 学籍学位相关表格；
- 成绩相关表格；
- 培养方案 PDF；
- 本科专业目录；
- 研究生培养相关表格；
- 研究生招生专业目录；
- 学生医保和报销资料；
- 后勤、网络、人事、外事等扩展资料。

注意：部分附件页面可能设置验证码或访问限制。系统应优先保存来源页面、附件名称和附件入口，不绕过验证码，不批量下载受限制附件。

---

#### 6.1.6 服务入口导航

系统应支持根据用户角色推荐常用入口：

| 用户角色 | 推荐入口 |
|---|---|
| 学生 | 教务部、教务管理系统、培养方案、资料下载、就业指导中心、校医院、后勤服务、网络服务、融合式门户 |
| 研究生 | 研究生处、研究生招生、培养管理、学位管理、相关下载、导师队伍 |
| 教师 | OA系统、邮箱、VPN、人力资源系统、科研项目系统、资产管理系统、网络服务、教务部 |
| 考生 / 家长 | 本科招生、研究生招生、专业目录、招生章程、录取情况、学院联系方式 |
| 访客 | 学校概况、机构设置、校园风光、校区地址、人才招聘、采购招标 |
| 管理员 | 数据采集、知识库更新、链接检测、内容审核、统计分析 |

---

#### 6.1.7 部门联系方式查询

系统应将可公开联系方式抽取成结构化数据，例如：

- 学校联系电话；
- 校区地址；
- 总务后勤部联系方式；
- 网络报障电话；
- 现代教育技术中心电话；
- 研究生处联系电话；
- 招生咨询方式；
- 校医院地点和服务时间。

当用户问“网络坏了找谁”“维修科电话是多少”“研究生招生电话是多少”时，系统优先调用结构化查询工具，而不是只依赖大模型生成。

---

#### 6.1.8 新闻公告检索

系统应支持：

- 按关键词搜索公告；
- 按栏目搜索学校要闻、校园快讯、通知公告；
- 查询最新招生就业通知；
- 查询后勤、网络、校医院等二级站点通知；
- 将结果按发布时间排序；
- 对时效性强的信息明确显示发布日期。

---

#### 6.1.9 无依据兜底

当知识库没有检索到可靠资料时，系统必须提示：

> 未在当前已采集的仲恺农业工程学院公开资料中找到可靠依据，建议访问对应部门官网或联系学校相关部门确认。

系统不得编造：

- 电话；
- 地址；
- 开放时间；
- 报销比例；
- 招生计划；
- 专业设置；
- 办事流程；
- 个人数据。


---

#### 6.1.10 Agent 主动任务路由

系统应体现 Agent 的主动判断能力，而不是固定调用某一个检索接口。

Agent 至少需要完成以下判断：

| 用户问题类型 | Agent 处理方式 |
|---|---|
| “学校有几个校区？” | 调用学校概况 RAG |
| “学校有哪些学院？” | 调用机构结构化查询工具 |
| “补办学生证申请表在哪里？” | 调用资料下载工具 + 教务下载 RAG |
| “数据科学与大数据技术培养方案在哪里？” | 调用专业查询工具 + 智能文档索引 |
| “2026 年研究生招生章程讲了什么？” | 调用智能文档问答工具 |
| “本科招生章程和研究生招生章程有什么区别？” | 调用多文档对比工具 |
| “网络报障找谁？” | 调用联系方式工具 |
| “学校有没有某个未公开服务入口？” | 触发无依据兜底 |

Agent 主动能力至少包括：

1. **意图识别**：识别用户是在问学校信息、找资料、查入口、问流程还是读文档；
2. **任务拆解**：复杂问题拆成“检索资料 + 查询结构化数据 + 生成答案”；
3. **工具选择**：自动选择 RAG、文档问答、专业查询、联系方式查询或服务入口查询；
4. **证据整合**：把多个来源的结果合并为一段清晰回答；
5. **可靠性判断**：低置信度或无来源时拒绝编造；
6. **追问建议**：当用户问题模糊时，主动提示可进一步查询的方向。

---

#### 6.1.11 智能文档功能

除官网网页信息外，系统还应将官网中的 PDF、DOC、DOCX、章程、制度、培养方案、申请表和办事指南转化为“智能文档”。

智能文档不是简单的文件下载列表，而是面向文档内容的 AI 能力。

系统应支持：

| 智能文档能力 | 说明 |
|---|---|
| 文档问答 | 用户围绕某个文档提问，系统基于文档片段回答 |
| 文档摘要 | 自动总结招生章程、培养方案、医保政策、申请表说明 |
| 关键字段抽取 | 提取适用对象、办理材料、办理地点、联系电话、发布日期 |
| 办事清单生成 | 根据申请表或办事指南生成“需要准备什么” |
| 跨文档检索 | 同时检索多个相关文档，返回最相关来源 |
| 跨文档对比 | 对比本科招生章程、研究生招生章程或不同专业培养方案 |
| 来源定位 | 展示文档名称、来源页面、页码或段落片段 |
| 文档推荐 | 根据用户问题推荐相关文档和附件入口 |

示例问题：

- 这份 2026 年硕士研究生招生章程主要讲了什么？
- 计算机科学与技术专业培养方案里有哪些核心课程？
- 免修申请表适合什么情况使用？
- 学生医保报销材料有哪些？
- 本科招生章程和研究生招生章程有什么区别？
- 帮我从这个办事指南里整理办理流程。
- 根据这些资料，我应该下载哪个表格？

智能文档功能是本项目区别于普通网站导航系统的重要 AI 亮点。

---

### 6.2 非功能性需求

| 需求 | 说明 |
|---|---|

| PDF 附件 | 培养方案、规章制度、招生专业目录 |
| DOC / DOCX 附件 | 专业目录、申请表、下载表格 |
| ZIP 附件 | 研究生招生考试大纲等资料包 |
| 结构化列表 | 学院列表、服务入口、职位信息、联系方式 |
| 时间型信息 | 新闻公告、招生通知、就业岗位、后勤通知 |
| 人工整理 FAQ | 高频问题的标准问答补充 |

### 7.3 资料采集方式

建议采用“自动采集 + 人工审核 + 结构化入库”的方式。

```text
确定官网与二级站点入口
  ↓
爬取公开栏目链接
  ↓
过滤无关导航、页脚、图片说明和重复内容
  ↓
提取标题、正文、发布时间、来源部门、URL
  ↓
识别附件名称、附件类型、附件入口
  ↓
按模块分类：概况 / 机构 / 专业 / 教务 / 招生 / 研究生 / 就业 / 后勤 / 网络 / 医疗
  ↓
转换为 Markdown / JSON
  ↓
人工抽查关键页面
  ↓
切分文本并生成 Embedding
  ↓
写入向量库和结构化数据库
```

---

### 7.4 资料筛选原则

优先采集：

1. 与学生、教师了解学校直接相关的信息；
2. 官网或二级站点公开发布的信息；
3. 有明确标题、发布时间、来源 URL 的信息；
4. 内容稳定、可长期复用的信息；
5. 可支撑问答、导航、下载、流程说明的信息；
6. 能抽取为结构化数据的信息，例如学院、专业、联系方式、系统入口。

暂不采集：

1. 需要登录后才能访问的个人数据；
2. 涉及学生个人信息、成绩、课表、财务、处分等敏感内容；
3. 过旧且无参考价值的通知；
4. 无法确认来源的第三方转载内容；
5. 需要验证码且不适合自动抓取的附件内容；
6. 与项目目标无关的宣传图、装饰图、重复导航。

## 8. 系统功能模块设计



### 8.0 功能设计主线：AI / Agent 优先

本项目功能设计应采用“AI / Agent 优先”的表达方式，而不是“栏目堆叠式”的表达方式。

推荐表达顺序：

```text
AI Agent 主控
  ↓
意图识别与任务路由
  ↓
RAG 检索 / 智能文档 / 结构化工具 / 服务入口工具
  ↓
可信回答与来源引用
  ↓
前端交互与资料展示
```

也就是说，学校概况、机构学院、专业培养、教务资料、研究生服务、后勤网络医疗等模块不是彼此孤立的信息页面，而是 Agent 可以主动调用的能力组件。

最终系统应体现：

- 用户不用知道资料在哪个部门；
- 用户不用知道官网栏目名称；
- 用户不用自己打开多个 PDF 对比；
- 用户只需提出自然语言问题；
- Agent 自动判断、检索、读取、对比、总结并给出来源。

### 8.12 智能文档中心模块

智能文档中心是本项目的重点 AI 功能之一，应与“资料下载中心”区分开。

资料下载中心解决的是：

> 用户要下载哪个文件？

智能文档中心解决的是：

> 用户不想自己读完整文件，希望 AI 帮他理解、总结、问答、提取和对比。

#### 8.12.1 智能文档来源

| 文档来源 | 示例 |
|---|---|
| 官网网页长文 | 学校简介、招生章程、通知公告、制度说明 |
| PDF 文件 | 本科培养方案、研究生招生专业目录、政策文件 |
| Word 文件 | 专业目录、申请表、办事材料 |
| 表格类附件 | 联系方式、计划表、统计表 |
| 压缩包资料 | 研究生考试大纲等资料包的元数据和可解析文件 |

#### 8.12.2 智能文档功能

| 功能 | 说明 |
|---|---|
| 文档对话 | 用户选择某个文档后，可以围绕该文档连续提问 |
| 文档摘要 | 自动生成短摘要、详细摘要和要点列表 |
| 目录识别 | 从 PDF 或长文中识别章节结构 |
| 关键信息抽取 | 抽取材料、时间、地点、电话、对象、流程 |
| 多文档对比 | 对比不同年份招生章程、不同专业培养方案 |
| 办理流程生成 | 从通知或申请表说明中生成步骤清单 |
| 问题推荐 | 根据文档自动生成用户可能关心的问题 |
| 引用定位 | 回答附带文档名、页码、章节或片段 |
| 文档标签 | 自动标记“招生”“教务”“研究生”“医保”“培养方案”等分类 |

#### 8.12.3 智能文档示例场景

| 用户问题 | 系统能力 |
|---|---|
| 这份招生章程适合哪些考生重点看？ | 文档摘要 + 关键条款提取 |
| 帮我总结数据科学与大数据技术培养方案 | PDF 文档问答 + 摘要 |
| 这个申请表需要准备什么材料？ | Word 表格解析 + 办事清单生成 |
| 研究生请假和缓考资料有什么区别？ | 多文档检索 + 对比 |
| 本科招生章程里关于录取规则怎么说？ | 文档定位问答 + 来源引用 |
| 把医保报销说明整理成步骤 | RAG 检索 + 流程生成 |

#### 8.12.4 智能文档与 RAG 的关系

智能文档功能本质上是面向文档对象的 RAG。

普通 RAG 的检索单位是“知识片段”，而智能文档的核心对象是“文档”。

```text
官网资料 / PDF / Word / 表格
  ↓
文档解析
  ↓
章节识别
  ↓
文本切分
  ↓
Embedding 向量化
  ↓
文档级索引 + 片段级索引
  ↓
用户围绕文档提问
  ↓
检索相关章节和片段
  ↓
生成带引用的文档回答
```

因此，系统中应同时存在：

- **全站 RAG**：回答“学校相关问题”；
- **文档 RAG**：回答“某份文档里怎么说”；
- **结构化工具**：回答“电话、链接、专业、附件在哪里”。

## 10. RAG 在项目中的作用

### 10.1 RAG 解决的问题

RAG 主要解决：

- 大模型不了解仲恺农业工程学院的真实信息；
- 学校公开资料分散在多个站点；
- 用户不知道去哪找资料；
- 大模型可能编造学校电话、地点、流程；
- 用户需要看到答案来源；
- 网站信息更新后需要可持续同步。

---

### 10.2 RAG 知识库范围

第一版知识库建议包含：

| 知识库集合 | 内容 |
|---|---|
| school_profile_docs | 学校概况、校区、历史、办学信息 |
| organization_docs | 机构设置、学院、部门、服务平台 |
| undergraduate_docs | 本科专业目录、培养方案、教务资料 |
| graduate_docs | 研究生招生、培养、学位、下载资料 |
| admission_docs | 本科招生章程、选考科目、录取情况 |
| employment_docs | 就业指导、职位信息、招聘活动、政策法规 |
| service_docs | 后勤、网络、校医院、公共服务 |
| news_docs | 学校要闻、通知公告、校园快讯 |
| download_docs | 各类附件标题、来源页面、文件类型、适用对象 |

---

### 10.3 文档切分策略

不同资料采用不同切分方式：

| 资料类型 | 切分策略 |
|---|---|
| 学校概况 | 按段落切分，保留标题和更新时间 |
| 机构设置 | 按机构类型切分，结构化抽取机构名和 URL |
| 专业目录 | 按专业记录切分，保留专业代码、名称、学院 |
| 培养方案 PDF | 按专业和章节切分，保留专业名称与附件来源 |
| 招生章程 | 按章节切分，例如报考须知、招生人数、奖助政策 |
| 教务下载 | 按下载条目切分，保留附件名和发布日期 |
| 后勤 / 网络 / 医疗服务指南 | 按服务事项切分，保留地点、电话、材料、流程 |

### 10.5 智能文档 RAG 设计

智能文档 RAG 是本项目 AI 能力的重点。

普通网站 RAG 解决的是“从官网网页中找到答案”，智能文档 RAG 解决的是“让用户不用打开完整文档，也能理解和使用文档”。

#### 10.5.1 文档处理流程

```text
采集官网文档入口
  ↓
下载或记录附件元数据
  ↓
解析 PDF / DOC / DOCX / HTML 长文
  ↓
提取标题、章节、正文、表格、页码
  ↓
生成文档摘要和标签
  ↓
按章节和语义切分
  ↓
建立文档级索引和片段级索引
  ↓
用户围绕文档提问
  ↓
检索相关片段
  ↓
生成带引用的回答
```

#### 10.5.2 文档索引设计

```text
document
- id
- title
- department
- category
- source_page_url
- file_url
- file_type
- publish_date
- summary
- tags
- parse_status
- created_at

document_chunk
- id
- document_id
- section_title
- page_number
- chunk_text
- embedding_id
- token_count
- chunk_index

document_qa_log
- id
- document_id
- question
- retrieved_chunks
- answer
- created_at
```

#### 10.5.3 智能文档回答要求

智能文档回答必须遵守：

1. 优先基于文档内容回答；
2. 显示文档名称；
3. 显示来源页面；
4. 如果能解析页码，则显示页码；
5. 如果无法确定答案，明确说明“文档中未检索到明确依据”；
6. 不把不同年份、不同类别、不同部门的文档混为一谈；
7. 涉及招生、医保、学籍、研究生管理等重要事项时，提示以官网最新文件为准。

---

### 10.6 Agent 与智能文档的协同

Agent 不只是调用 RAG，还应能判断什么时候进入“智能文档模式”。

| 用户表达 | Agent 判断 | 处理方式 |
|---|---|---|
| “这个文件讲了什么？” | 文档摘要 | 调用 document_summary |
| “培养方案里有哪些课程？” | 文档问答 | 调用 document_qa |
| “这两个章程有什么区别？” | 多文档对比 | 调用 document_compare |
| “我需要准备什么材料？” | 关键信息抽取 | 调用 document_extract |
| “帮我整理步骤” | 流程生成 | 调用 workflow_generate |
| “相关文件有哪些？” | 文档推荐 | 调用 document_recommend |

这样系统展示出来的就不是“搜索引擎”，而是一个能主动读文档、理解文档、使用文档的校园信息 Agent。

## 11. 工具调用设计

本项目的工具调用应尽量贴合仲恺官网公开数据，不建议第一阶段以天气查询作为核心工具。

### 11.1 第一阶段建议实现的工具

| 工具 | 类型 | 作用 |
|---|---|---|
| 学院机构查询工具 | SQLite / JSON | 根据学院名、部门名、服务类型返回官网入口 |
| 专业查询工具 | SQLite / JSON | 根据专业名、专业代码、学院查询本科专业信息 |
| 培养方案查询工具 | SQLite / JSON | 根据专业名返回培养方案来源页和附件信息 |
| 资料下载查询工具 | SQLite / JSON | 根据关键词查申请表、流程图、附件资料 |
| 服务入口查询工具 | SQLite / JSON | 查询 OA、邮箱、VPN、教务、就业、研究生、资产、人事等入口 |
| 联系方式查询工具 | SQLite / JSON | 查询后勤、网络、校医院、招生、研究生等公开电话 |
| 新闻公告检索工具 | SQLite / ElasticSearch / Meilisearch | 按关键词和日期查询公告 |
| 智能文档问答工具 | 向量库 + 文档索引 | 围绕 PDF、Word、章程、培养方案进行问答 |
| 文档摘要工具 | LLM + RAG | 自动总结长文档并生成要点 |
| 多文档对比工具 | RAG + LLM | 对比不同文档、不同年份、不同专业资料 |
| 文档信息抽取工具 | LLM + 规则 | 抽取材料、时间、地点、对象、电话、流程 |
| 链接有效性检测工具 | 定时脚本 | 检查来源 URL 和附件入口是否失效 |

## 15. MVP 最小可行版本

### 15.1 MVP 目标

MVP 不追求覆盖所有官网内容，而是先做一个“小而完整”的智能体闭环：

```text
官网公开资料
  ↓
数据采集与清洗
  ↓
结构化数据库 + 向量知识库
  ↓
RAG 检索 + 工具查询
  ↓
大模型生成可信回答
  ↓
前端展示答案、来源和附件入口
```

---

### 15.2 MVP 建议覆盖范围

第一版建议覆盖 6 个模块：

| MVP 模块 | 选择原因 |
|---|---|
| 学校概况与校区信息 | 官网资料稳定，适合作为基础知识问答 |
| 机构学院导航 | 官网结构清晰，适合做结构化查询 |
| 本科专业与培养方案 | 教务部资料完整，附件价值高 |
| 教务资料下载 | 学生高频需求，下载栏目清晰 |
| 研究生招生与研究生下载 | 研究生处资料丰富，适合扩展用户群 |
| 公共服务入口与联系方式 | 后勤、网络、校医院信息实用，适合工具调用 |

就业服务和新闻公告可作为 MVP 的增强模块；如果开发时间有限，可先做列表检索和入口导航，不必做复杂推荐。

---

### 15.3 MVP 必须实现的能力

1. 前端可以输入问题；
2. 后端可以返回回答；
3. 回答基于真实官网资料；
4. 至少支持一个向量知识库；
5. 至少支持三个结构化工具：
   - 专业查询工具；
   - 资料下载查询工具；
   - 联系方式 / 服务入口查询工具；
6. 至少实现一个智能文档功能：
   - 文档问答；
   - 文档摘要；
   - 关键字段抽取；
   - 多文档对比任选其一；
7. 回答展示来源；
8. 查询不到可靠依据时不编造；
9. 支持管理员重新构建知识库；
10. 提供部署说明和演示问题集。

## 19. 风险与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| 网站结构变化 | 官网栏目或二级站点链接可能变动 | 采集器配置化，定期做链接检测 |
| 附件下载受限 | 部分附件可能需要验证码或权限 | 保存来源页面和附件名，不绕过限制 |
| 信息过期 | 招生、就业、公告、校医院时间可能变化 | 显示发布时间，设置更新频率 |
| 数据范围过大 | 官网和二级站点信息很多 | MVP 只覆盖核心模块 |
| RAG 结果混乱 | 多个相似表格可能被误匹配 | 使用 metadata 过滤部门、年份、类别 |
| 大模型编造 | 没有资料时生成错误答案 | 设置必须引用来源和无依据兜底 |
| 登录系统不可采集 | OA、教务、人事、资产等需认证 | 只做入口导航，不抓取内部数据 |
| 隐私与安全 | 不应采集学生个人数据 | 限定公开网页，脱敏处理日志 |
| 前后端工作量大 | 全栈开发耗时 | 可先用 Streamlit 做 MVP，再升级 Vue/React |

## 22. 暂定项目简介

> 本项目面向仲恺农业工程学院学生、教师及访客，设计并实现一个以 Agent 为核心的大语言模型校园信息服务系统。系统采集学校官网及公开二级站点中的学校概况、机构设置、学院专业、本科培养方案、招生就业、研究生教育、教务资料下载、后勤服务、网络服务、校医院和公共服务入口等信息，并将网页、PDF、Word、章程、制度、申请表和培养方案转化为可问答、可摘要、可抽取、可对比的智能文档知识库。用户可通过 Web 界面以自然语言提问，Agent 根据问题类型主动选择 RAG 检索、智能文档问答、结构化工具查询或多工具协同流程，生成带来源依据的回答，并提供相关网页、附件、文档片段和服务入口，从而帮助学生和教师更高效地了解学校、阅读资料、查找表格和定位服务。

## 23. 备注

本项目的关键不是一次性复制完整官网，而是完成一个可靠闭环：

```text
公开官网资料 + 官网文档附件
  ↓
采集清洗与文档解析
  ↓
结构化数据 + 向量知识库 + 智能文档索引
  ↓
Agent 意图识别与任务路由
  ↓
RAG 检索 + 文档问答 + 工具查询
  ↓
可信回答生成
  ↓
来源、页码、附件和服务入口展示
  ↓
用户反馈与定期更新
```

当 MVP 稳定后，可以继续扩展：

- 更多学院官网；
- 图书馆详细服务；
- 信息公开资料；
- 招采信息；
- 人才招聘；
- 校友与基金；
- 校园地图；
- 智能推荐；
- 统一身份认证后的授权服务。
